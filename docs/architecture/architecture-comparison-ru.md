## 1. Резюме для руководства и команды (Executive Summary)

### 1.1. Какую техническую проблему мы решаем?

В корпоративном backend-приложении для операционного управления рестораном (**Ratatouille ERP**) предсказуемое и безопасное поведение при возникновении ошибок так же критично, как и успешная обработка запросов. До настоящего момента в ветке `dev` существовали четыре фундаментальных архитектурных ограничения в части обработки исключений:

1. **Несогласованность формата ответов об ошибках (фрагментированный API-контракт):**
   - Когда роут явно выбрасывал `HTTPException(status_code=404, detail="Plato no encontrado")`, клиент получал компактный JSON: `{"detail": "Plato no encontrado"}`.
   - Однако при ошибке валидации входных данных в Pydantic v2 (`RequestValidationError`, HTTP `422`) FastAPI по умолчанию возвращал сложный массив технических объектов на английском языке (`[{"type": "...", "loc": ["body", "..."], "msg": "Field required", "input": ...}]`), раскрывая внутренние имена схем и само поле `input` с пользовательскими данными.
   - При нарушении ограничений целостности PostgreSQL (`IntegrityError` из-за дубликата уникального ключа или несуществующего внешнего ключа), если оно не было перехвачено предварительным `SELECT`, либо при непредвиденном сбое во время выполнения приложение могло вернуть нестандартизированный ответ `500` или оставить сессию SQLAlchemy в невалидном состоянии (`PendingRollbackError`).
2. **Сильная связность бизнес-логики с транспортным уровнем HTTP:**
   - Проверки бизнес-правил выполнялись непосредственно в файлах роутов (`app/api/dish_routes.py`, `app/api/category_routes.py`) с выбросом `fastapi.HTTPException`. Это затрудняет повторное использование сервисного слоя (`app/services/`) из CLI-скриптов, фоновых задач или модульных тестов без прямой зависимости от FastAPI/Starlette.
3. **Отсутствие сквозной трассировки (`X-Request-ID`) и маскирования секретов в логах:**
   - Запросы не имели уникального идентификатора корреляции (`correlation_id`), а логи не форматировались в структурированный JSON и не маскировали пароли, JWT-токены или строки подключения к БД (`DATABASE_URL` / DSN).
4. **Расхождение схемы OpenAPI 3.1 с фактическими ответами об ошибках:**
   - Интерактивная документация Swagger UI (`/docs`) по умолчанию отображала стандартную схему `HTTPValidationError` для кода `422` и не содержала единого каталога ответов для кодов `400`, `401`, `403`, `404`, `409`, `422` и `500`.

### 1.2. Почему исходный Pull Request вызвал конфликты слияния?

Исходный Pull Request (**PR #6**) был по ошибке открыт с целевой веткой `main` и базировался на коммите `abe6b6f` (*Merge pull request #7 from mxu-init/feat/SGR-70-allergen-model*). Параллельно с этим:
- В ветку `origin/dev` был влит **PR #9** (`refactor/code-refinement`, коммит `daac6dd`), затронувший 17 файлов: в нём был добавлен контекстный менеджер жизненного цикла `lifespan` с автоматической инициализацией справочных данных при старте (`reference_service.ensure_reference_data_on_startup()`), настроены абсолютные пути к статическим файлам (`STATIC_DIR`), добавлен эндпоинт `/favicon.ico`, модели SQLAlchemy разделены на отдельные модули с единым пакетом `app/models/__init__.py`, а текстовая колонка `dishes.allergens` заменена на связь «многие-ко-многим» через таблицу `dish_allergens`.
- Поскольку и PR #9 в `dev`, и ветка `feat/errors-handler` существенно изменили `app/main.py` (первый добавил `lifespan` и `STATIC_DIR`, а вторая — фабрику `create_app()`, middleware и глобальные обработчики исключений), возник прямой конфликт слияния в файле `app/main.py`.

### 1.3. Почему целевой веткой интеграции является `dev`, а НЕ `main`?

В соответствии с принятым в команде процессом разработки (Gitflow):
- **`origin/dev`** — основная интеграционная ветка, в которой объединяются и тестируются все завершённые задачи текущего спринта (включая справочник аллергенов SGR-70 и рефакторинг архитектуры из PR #9).
- **`origin/main`** предназначена исключительно для стабильных релизов. Более того, проведённый аудит показал, что в `origin/main` напрямую попали два коммита (`266af6a` и `daeb2d2`), относящиеся к задаче CRUD столов, для которой уже открыт отдельный Pull Request в `dev` (**PR #10**, `feature/sgr-23-tables-crud` → `dev`).
- Следовательно, слияние в `main` нарушило бы ветвление проекта и привело бы к обходу интеграционного тестирования в `dev`.

### 1.4. Предлагаемые архитектурные улучшения и итоговый результат

Интеграция ветки `feat/errors-handler` поверх актуального состояния `origin/dev` обеспечивает:
- **Единый контракт ошибок на испанском языке (`ErrorResponse`):** Любая ошибка `4xx` или `5xx` (включая ошибки валидации Pydantic `422` и ошибки PostgreSQL) возвращает строго `{"detail": "Понятное сообщение на испанском языке"}`.
- **Полное сохранение функциональности `dev`:** Без малейших потерь сохранены `lifespan` (`ensure_reference_data_on_startup`), `STATIC_DIR`, `/favicon.ico`, `/docs/favicon.ico`, `/health`, `/health/db` и все существующие роутеры (`dishes`, `categories`, `allergens`, `test`).
- **Транспортно-независимая иерархия доменных исключений (`AppError`):** Позволяет сервисам выбрасывать семантические исключения (`NotFoundError`, `ConflictError`, `DomainValidationError` и др.) без импорта FastAPI при сохранении 100% обратной совместимости с существующими роутами, использующими `HTTPException`.
- **Автоматическая трансляция ошибок PostgreSQL (`SQLSTATE`) и гарантированный `session.rollback()`:** Предотвращает утечку деталей SQL-запросов и защищает сессии SQLAlchemy от блокировки в состоянии `PendingRollbackError`.
- **Чистый ASGI Middleware (`CorrelationIdMiddleware`) и структурированное JSON-логирование с маскированием секретов (`[REDACTED]`).**

## 2. Текущая архитектура в ветке `dev`

Перед внесением изменений был детально проанализирован исходный код ветки `origin/dev` (коммит `daac6dd`). Ниже описано фактическое устройство приложения в `dev`.

### 2.1. Инициализация приложения и роль `app/main.py`

В `origin/dev` файл `app/main.py` состоит из 50 строк и выполняет всю настройку приложения непосредственно в глобальной области видимости модуля (во время импорта файла):

```python
BASE_DIR = Path(__file__).resolve().parent.parent
STATIC_DIR = BASE_DIR / "static"

@asynccontextmanager
async def lifespan(app: FastAPI):
    reference_service.ensure_reference_data_on_startup()
    yield

app = FastAPI(
    title=settings.APP_NAME,
    version=settings.APP_VERSION,
    description=settings.APP_DESCRIPTION,
    lifespan=lifespan,
)

os.makedirs(STATIC_DIR / "uploads", exist_ok=True)
app.mount("/static", StaticFiles(directory=str(STATIC_DIR)), name="static")
```

### 2.2. Регистрация роутеров

В `origin/dev` файл `app/main.py` напрямую подключает четыре модуля маршрутизации к глобальному объекту `app`:
1. `test_routes.router` (`prefix="/test"`, `tags=["Test"]`)
2. `dish_routes.router` (`prefix="/dishes"`, `tags=["Platos"]`)
3. `category_routes.router` (`prefix="/categories"`, `tags=["Categorías"]`)
4. `allergen_routes.router` (`prefix="/allergens"`, `tags=["allergens"]`)

Также непосредственно в `app/main.py` объявлены четыре служебных эндпоинта:
- `GET /` → возвращает `"API Template"`.
- `GET /favicon.ico` и `GET /docs/favicon.ico` → возвращают `FileResponse(STATIC_DIR / "favicon.ico")`.
- `GET /health` → возвращает `{"status": "ok"}`.
- `GET /health/db` → выполняет `SELECT 1` через `engine` SQLAlchemy для проверки соединения с PostgreSQL.

### 2.3. Управление запуском (`lifespan`) и справочными данными

Одним из ключевых улучшений в `origin/dev` (внесённым в PR #9) стала система управления базовыми справочниками:
- **`app/core/reference_data.py`**: Определяет единый источник истины для 5 базовых категорий меню (`BASE_CATEGORIES`: *Entrantes, Primeros, Segundos, Postres, Bebidas*) и 14 обязательных аллергенов ЕС (`EU_ALLERGENS`, Регламент ЕС 1169/2011).
- **`app/services/reference_service.py`**: Реализует функцию `ensure_reference_data_on_startup()`. При запуске FastAPI внутри `lifespan` она проверяет наличие таблиц `categories` и `allergens` через `sqlalchemy.inspect(engine)`. Если миграции Alembic уже применены, функция идемпотентно дозаполняет недостающие базовые категории и аллергены в рамках одной транзакции; если таблицы ещё не созданы, выводит `logger.warning` и позволяет приложению запуститься без сбоя.

### 2.4. Middleware, обработка исключений, логирование и OpenAPI в `origin/dev`

- **Middleware:** В `origin/dev` нет пользовательских middleware. Используется только стандартный внутренний стек Starlette/FastAPI (`ServerErrorMiddleware`, `ExceptionMiddleware`, `AsyncExitStackMiddleware`).
- **Обработка HTTP-исключений и ошибок валидации:**
  - В `dish_routes.py` и `category_routes.py` бизнес-проверки (длина названия, положительная цена, существование категории или аллергенов) выполняются вручную в коде роутов с вызовом `raise HTTPException(...)` и сообщениями на испанском языке.
  - Однако если Pydantic отклоняет входной JSON или параметры запроса (например, в `POST /categories/` или `PUT /dishes/{id}`), срабатывает стандартный обработчик FastAPI, возвращающий англоязычный массив ошибок Pydantic (`loc`, `msg`, `type`, `input`).
  - Глобальные обработчики для `SQLAlchemyError` и непредвиденных исключений `Exception` отсутствуют.
- **Логирование и трассировка:**
  - Централизованная конфигурация логирования отсутствует. В `database_connection.py` включён `echo=True` на уровне `engine`, а в `reference_service.py` используется стандартный `logging.getLogger(__name__)`.
  - У HTTP-запросов нет заголовка `X-Request-ID` или идентификатора корреляции.
- **OpenAPI:**
  - Используется стандартная генерация схемы FastAPI без переопределения ответов `422` и без единой модели ошибок.

## 3. Предлагаемая архитектура (`feat/errors-handler`, интегрированная с `dev`)

Интегрированная архитектура объединяет все наработки `origin/dev` (`lifespan`, справочные данные, модульные модели, абсолютные пути к статике) с централизованной подсистемой обработки ошибок, трассировки и безопасности из `feat/errors-handler` (`SGR-49`).

### 3.1. Фабрика приложения `create_app()` и сохранение `lifespan`

Вместо разрозненной настройки глобального объекта `app` при импорте модуля, `app/main.py` инкапсулирует сборку приложения в функции `create_app() -> FastAPI`, а в последней строке файла создаёт экземпляр `app = create_app()`, благодаря чему команда запуска `uvicorn app.main:app --reload` работает без каких-либо изменений.

Внутри `create_app()` выполняются следующие шаги:
1. Инициализируется структурированный JSON-логгер (`configure_logging()`).
2. Создаётся экземпляр `FastAPI`, в который передаются `lifespan=lifespan` (вызывающий `reference_service.ensure_reference_data_on_startup()`) и каталог ответов `responses=COMMON_ERROR_RESPONSES`.
3. Регистрируются `CorrelationIdMiddleware` и глобальные обработчики исключений через `register_exception_handlers(application)`.
4. Создаётся директория `STATIC_DIR / "uploads"` и монтируется `/static` с использованием абсолютного пути `STATIC_DIR`.
5. Подключаются все роутеры из `dev` (`test_routes`, `dish_routes`, `category_routes`, `allergen_routes`) и демонстрационный роутер контрактов ошибок (`routes.router`).
6. Регистрируются служебные маршруты `/`, `/favicon.ico`, `/docs/favicon.ico`, `/health` и `/health/db`.
7. Вызывается `configure_openapi(application)` для приведения схемы OpenAPI 3.1 в полное соответствие с моделью `ErrorResponse`.

### 3.2. Критическая архитектурная оценка: Преимущества, компромиссы и обоснование

Как инженеры-архитекторы, мы не должны считать любое усложнение кода автоматическим улучшением. Оценим объективно каждое архитектурное решение, привносимое веткой `feat/errors-handler`:

- **Оправдано ли использование фабрики `create_app()` для проекта текущего масштаба?**
  - *Преимущества:* Позволяет создавать изолированные экземпляры приложения в автотестах без разделяемого глобального состояния и побочных эффектов при импорте; делает порядок инициализации явным и детерминированным (логирование → FastAPI с lifespan → middleware → обработчики исключений → статика → роутеры → OpenAPI).
  - *Недостатки / когнитивная нагрузка:* Добавляет один уровень абстракции по сравнению с плоским скриптом из базовых примеров FastAPI.
  - *Вердикт:* **Полностью оправдано**, так как наличие строки `app = create_app()` в конце модуля сохраняет 100% совместимость с привычным запуском через Uvicorn, одновременно повышая тестируемость.
- **Как `create_app()` взаимодействует с `lifespan`?**
  - Нативно и без конфликтов: асинхронный контекстный менеджер `lifespan` передаётся в конструктор `FastAPI(..., lifespan=lifespan)` внутри `create_app()`. При запуске сервера Uvicorn или при использовании `with TestClient(app) as client:` в тестах Starlette автоматически вызывает `ensure_reference_data_on_startup()`.
- **Насколько корректна реализация `CorrelationIdMiddleware` как Pure ASGI Middleware?**
  - *Ключевое преимущество:* Стандартный класс `BaseHTTPMiddleware` в Starlette имеет известные накладные расходы и особенности работы с `ContextVar` при пробросе исключений. Реализация `CorrelationIdMiddleware` напрямую через интерфейс ASGI (`__call__(self, scope, receive, send)`) — это образцовое техническое решение: оно считывает или генерирует `X-Request-ID`, сохраняет его в `correlation_id_ctx` (`ContextVar`) и `scope["state"]["correlation_id"]`, гарантированно добавляет заголовок в `http.response.start` и очищает контекст в блоке `finally`.
- **Какие элементы требуют внимания или являются потенциально избыточными?**
  1. **Демо-роутер `app/api/routes.py` (`/errores-demo`):** Содержит 5 эндпоинтов для интерактивной проверки контрактов ошибок (`403`, `404`, `409`, `422`, `500`) прямо из Swagger UI. Для приёмки задачи `SGR-49` это очень удобно, однако в будущем при подготовке промышленного релиза его стоит либо включать только при `settings.DEBUG == True`, либо оставить исключительно в тестовых фикстурах.
  2. **Защита эндпоинта `/favicon.ico`:** В ветке `origin/dev` функция `favicon()` безусловно возвращала `FileResponse(STATIC_DIR / "favicon.ico")`. Но сам файл `static/favicon.ico` отсутствует в Git-репозитории. При включении глобального обработчика исключений отсутствие файла на диске вызывает `RuntimeError` внутри Starlette, что приводило к ответу `500`. В ходе интеграционного тестирования мы выявили эту проблему и добавили проверку `if favicon_path.is_file(): return FileResponse(favicon_path)`, возвращая корректный статус `204 No Content`, если файл иконки отсутствует.

### 3.3. Диаграмма интегрированной архитектуры

```
+-----------------------------------------------------------------------------+
|                          HTTP-клиент / Swagger UI                           |
+--------------------------------------+--------------------------------------+
                                       | HTTP-запрос (с X-Request-ID или без)
                                       v
+-----------------------------------------------------------------------------+
|            CorrelationIdMiddleware (Pure ASGI - logging_config.py)          |
|  1. Извлекает заголовок X-Request-ID или генерирует новый UUIDv4            |
|  2. Записывает ID в ContextVar (correlation_id_ctx) и request.state         |
|  3. Гарантирует присутствие X-Request-ID во всех HTTP-ответах (2xx/4xx/5xx) |
+--------------------------------------+--------------------------------------+
                                       |
                                       v
```

## 5. Детальный разбор изменений в `app/main.py`

У участников команды возник закономерный вопрос: почему файл `app/main.py` увеличился с ~50 до ~145 строк и зачем в нём появились функции `create_app()` и `configure_openapi()`? В этом разделе мы подробно и доступно объясним назначение каждого блока, чтобы у команды было полное понимание архитектурной логики.

### 5.1. За что отвечал `app/main.py` раньше в ветке `dev`?

В `origin/dev` файл `app/main.py` выполнял 5 базовых задач в виде линейного скрипта:
1. Вычислял пути к директориям (`BASE_DIR` и `STATIC_DIR`).
2. Объявлял контекстный менеджер `lifespan` для проверки базовых категорий и аллергенов при старте.
3. Создавал экземпляр `app = FastAPI(...)` и монтировал папку `/static`.
4. Подключал 4 роутера (`test`, `dish`, `category`, `allergen`).
5. Объявлял вспомогательные маршруты `/`, `/favicon.ico`, `/docs/favicon.ico`, `/health` и `/health/db`.

### 5.2. За что отвечает `app/main.py` после интеграции?

После интеграции `feat/errors-handler` модуль `app/main.py` выступает в роли **Корня композиции приложения (*Composition Root*)**. В нём нет бизнес-логики или словарей перевода ошибок (они вынесены в модули `app/core/`), но именно здесь все инфраструктурные слои собираются в единое целое в трёх чётко разделённых блоках:

1. **Управление жизненным циклом (`lifespan`, строки 31–34):**
   Полностью сохранён код из `dev`, вызывающий `reference_service.ensure_reference_data_on_startup()`.
2. **Кастомизация схемы OpenAPI 3.1 (`configure_openapi`, строки 37–84):**
   По умолчанию FastAPI автоматически добавляет к каждому маршруту с параметрами ответ `422 Unprocessable Entity`, ссылающийся на стандартную схему `HTTPValidationError`. Поскольку наш глобальный обработчик ошибок заменяет этот формат на единую схему `ErrorResponse` (`{"detail": "..."}`), без обновления OpenAPI-схемы документация в `/docs` вводила бы разработчиков в заблуждение. Функция `configure_openapi()` удаляет устаревшие схемы `HTTPValidationError`/`ValidationError` и перенаправляет все ответы `422` на `#/components/schemas/ErrorResponse`.
3. **Фабрика приложения (`create_app`, строки 87–142) и глобальный экземпляр (`app = create_app()`, строка 145):**
   Конфигурирует логирование, создаёт экземпляр `FastAPI` (с `lifespan` и `COMMON_ERROR_RESPONSES`), подключает `CorrelationIdMiddleware`, регистрирует 5 глобальных обработчиков исключений (`register_exception_handlers`), монтирует `STATIC_DIR` и регистрирует все роутеры и служебные эндпоинты.

### 5.3. Зачем нужна фабрика приложения `create_app()`?

Когда объект `app = FastAPI()` создаётся и настраивается прямо в глобальной области видимости модуля, любой тестовый файл при импорте `from app.main import ...` немедленно выполняет весь глобальный код. Использование функции-фабрики `create_app()` даёт два важных преимущества:
- В автотестах можно вызывать `create_app()`, получая чистый, изолированный экземпляр приложения для каждого теста без взаимного влияния тестов друг на друга.
- Поскольку в последней строке файла остаётся `app = create_app()`, **способ запуска приложения для команды вообще не меняется**: команда `uvicorn app.main:app --reload` работает точно так же, как и раньше.

### 5.4. Почему middleware и обработчики исключений регистрируются централизованно?

Если бы перехват `SQLAlchemyError`, перевод ошибок Pydantic или генерация заголовка `X-Request-ID` выполнялись вручную внутри каждого файла маршрутов (`dish_routes.py`, `category_routes.py`, `table_routes.py` и т.д.), это привело бы к массовому дублированию кода, а любая забытая проверка оборачивалась бы необработанной ошибкой `500`. Централизованная регистрация в `create_app()` через `application.add_middleware(CorrelationIdMiddleware)` и `register_exception_handlers(application)` **автоматически защищает все существующие и будущие роутеры проекта**.

### 5.5. Разделение ответственности против неоправданного усложнения

Важно чётко разграничивать **случайную сложность** (переусложнение кода без практической пользы) и **архитектурное разделение ответственности**:
- В `app/main.py` **нет** регулярных выражений, таблиц перевода SQLSTATE или логики отката транзакций — вся эта функциональность аккуратно изолирована в профильных модулях (`app/core/exceptions.py`, `app/core/error_translations.py`, `app/core/handlers.py`, `app/core/logging_config.py`, `app/schemas/errors.py`).
- Увеличение объёма `app/main.py` обусловлено исключительно функцией `configure_openapi()` (~45 строк), необходимой для корректного отображения `ErrorResponse` в Swagger UI, и обёрткой `create_app()`.

## 8. Поток обработки ошибок и жизненный цикл HTTP-запроса

### 8.1. Пошаговое прохождение HTTP-запроса через систему

```
[1. Входящий HTTP-запрос]
       |
       v
[2. CorrelationIdMiddleware (Pure ASGI)]
       |-- Считывает заголовок 'X-Request-ID' (или генерирует новый UUIDv4)
       |-- Сохраняет ID в ContextVar 'correlation_id_ctx' и 'request.state.correlation_id'
       |
       v
[3. Маршрутизация и валидация входных данных (FastAPI / Pydantic v2)]
       |-- Ошибка валидации типов/полей тела запроса или query-параметров?
       |     +-- ДА --> Выбрасывается RequestValidationError
       |                --> Перехватывается в request_validation_error_handler()
       |                --> extract_field_name() + translate_validation_errors()
       |                --> Логируется WARNING в JSON (с correlation_id, без поля 'input')
       |                --> HTTP-ответ 422: {"detail": "Error en el campo 'X': ..."}
       |
       |-- Входная валидация пройдена успешно?
             +-- ДА --> Вызов контроллера / эндпоинта / сервиса
                          |
                          +-- Сценарий A: Успешное выполнение (200 / 201 / 204)
                          |     --> Middleware добавляет заголовок 'X-Request-ID'
                          |     --> Клиент получает штатный JSON-ответ
                          |
                          +-- Сценарий B: Бизнес-правило выбрасывает AppError (NotFoundError, ConflictError...)
                          |     --> Перехватывается в app_error_handler()
                          |     --> Сопоставляет класс исключения с HTTP-кодом (404, 409, 403, 422, 503, 500)
                          |     --> Маскирует чувствительные данные через redact_sensitive_data()
                          |     --> HTTP-ответ с {"detail": "<сообщение на испанском>"}
                          |
                          +-- Сценарий C: Существующий роут выбрасывает HTTPException / StarletteHTTPException
                          |     --> Перехватывается в http_exception_handler()
                          |     --> Сохраняет испанский текст или переводит стандартный английский detail
                          |     --> Сохраняет заголовки (например, WWW-Authenticate) + X-Request-ID
                          |     --> HTTP-ответ с {"detail": "<сообщение на испанском>"}
                          |
                          +-- Сценарий D: Ошибка целостности PostgreSQL (через handle_db_exceptions или глобально)
                          |     --> Немедленно выполняет session.rollback()
                          |     --> Извлекает 5-символьный SQLSTATE (23505, 23503...) и constraint_name
                          |     --> Преобразует в ConflictError (409) или DomainValidationError (422)
                          |     --> Никогда не раскрывает клиенту текст SQL-запроса или имена таблиц
                          |
                          +-- Сценарий E: Непредвиденное исключение (RuntimeError, KeyError, ZeroDivisionError...)
                                --> Перехватывается в unhandled_exception_handler()
                                --> Логирует ERROR в JSON с внутренним типом ошибки и маскированием DSN ([REDACTED])
                                --> HTTP-ответ 500: {"detail": "Error interno del servidor"}
```

### 8.2. Конкретные примеры реальных ответов об ошибках

### 9.3. Проблемы, обнаруженные и устранённые в ходе тестирования

1. **Конфликт сбора тестов Pytest с файлом `app/models/test_model.py`:**
   - *Предсуществующая проблема в `dev`:* При запуске `pytest` без указания папки Pytest пытался импортировать файл `app/models/test_model.py` как тестовый модуль из-за префикса `test_`. Поскольку этот модуль уже был импортирован через `test_controller.py`, SQLAlchemy выбрасывал ошибку `InvalidRequestError: Table 'test' is already defined for this MetaData instance`.
   - *Решение:* Добавлен конфигурационный файл `pytest.ini` с параметром `testpaths = tests`, что полностью устранило ошибку без модификации `test_model.py`.
2. **Обработка `/favicon.ico` при отсутствии файла `static/favicon.ico`:**
   - *Обнаруженная проблема:* В `origin/dev` эндпоинт `favicon()` возвращал `FileResponse(STATIC_DIR / "favicon.ico")` без проверки существования файла. Так как файла `static/favicon.ico` нет в репозитории, запрос к `/favicon.ico` вызывал `RuntimeError` в Starlette.
   - *Решение:* В `favicon()` добавлена проверка `if favicon_path.is_file(): return FileResponse(favicon_path)`, а при отсутствии файла возвращается корректный ответ `Response(status_code=204)`.
